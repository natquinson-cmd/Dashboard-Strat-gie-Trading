1. Contexte et objectifs

Ce document constitue le plan d'action pour le POC (Proof of Concept) de la partie Achat dans le cadre de la migration de SAP BW 7.5 on HANA vers SAP BW/4HANA en approche Greenfield.

1.1 Objectifs du POC

  • Valider la faisabilité de la reprise des données historiques depuis les InfoProviders BW 7.5
  • Tester les extracteurs standards (CDS views S/4HANA et/ou extracteurs 2LIS)
  • Mettre en place l'architecture cible sur 4 couches (A, W, D, R)
  • Valider la conversion de devises (devise EPFL / devise Achat) et la gestion multilingue
  • Déployer la chaîne complète jusqu'en Production (BFP)
  • Tracer le temps, les problèmes et les points de blocage

4.1 Stratégie de reprise des données

Approche retenue : double flux (historique 7.5 + courant S/4)

Les données Achats sont alimentées par deux flux distincts, unifiés dans une Calculation View pour le reporting :

  • Flux historique BW 7.5 : reprise du cube 0PUR_C01 depuis BWQ via DataSource ODP custom (ODP_BW / BWQCLNT100)
  • Flux courant S/4HANA : extraction via CDS views extraction-enabled depuis SFDCLNT223 (ODP_CDS), avec delta CDC

4.1.1 Flux historique – Reprise BW 7.5

Connexion RFC directe entre BW/4HANA (BFD) et BW 7.5 (BWQ) via le système source BWQCLNT100 (type ODP_BW).

Point technique : La DataSource d'export standard 80PUR_C01 est une DataSource 3.x, incompatible avec le protocole ODP utilisé par BW/4HANA. La transaction RODPS_OS_MIGRATE n'étant pas disponible sur BWQ (niveau de Support Pack insuffisant), la solution retenue est la création d'une DataSource ODP custom directement dans BFD, qui accède au cube 0PUR_C01 de BWQ via la connexion ODP_BW / BWQCLNT100.

Flux :

BWQ [0PUR_C01] —RFC (ODP_BW / BWQCLNT100)—→ BFD [DataSource ODP custom] → Transfo → DTP → A750PURC1 (ADSO Acquisition)

4.1.2 Flux courant – CDS views S/4HANA

Deux CDS views extraction-enabled ont été identifiées sur le système S/4HANA (SFDCLNT223) pour couvrir le périmètre POC :

CDS ViewNom DDICDataSource BFDADSO cibleDescriptionTable S/4Delta
C_PurOrdAcctAssgmtDEXCMMPURORDAADEXHA_CMMPURORDAADEXWMMPU002Imputations commande d'achatEKKNCDC
C_PurchaseOrderItemDEXCMMPOITMDEXHA_CMMPOITMDEXWMMPU001Postes commande d'achatEKKO / EKPOCDC

Pourquoi 2 CDS views : La CDS CMMPOITMDEX (postes EKPO) est la source principale : elle contient le fournisseur (SUPPLIER), le groupe de marchandises (MATERIALGROUP), l'organisation d'achat, ainsi que les montants et quantités de référence au niveau poste. La CDS CMMPURORDAADEX (imputations EKKN) apporte en complément les dimensions d'imputation comptable (GL_ACCOUNT, WBS_ELEMT, FUND) qui n'existent pas au niveau poste. Un LEFT JOIN entre les deux ADSOs est nécessaire dans la vue de reporting.

Important : Les montants et quantités doivent être pris depuis WMMPU001 (postes) et non depuis WMMPU002 (imputations), car les valeurs dans EKKN sont ventilées par ligne d'imputation (split accounting) et ne représentent que des fractions du montant total du poste.

Convention BW/4HANA – CDS views et nommage :

  • I_* (Interface views) : usage applicatif (Fiori, OData, ABAP) — non visibles dans Eclipse BW
  • C_*DEX (Extraction views) : annotées @Analytics.dataExtraction.enabled: true — visibles comme DataSource ODP_CDS
  • CMM* : nom DDIC runtime des CDS extracteurs (utilisé dans les tables IXTRCTNENBLDVW et RSODPABAPCDSVIEW)

Pour identifier les CDS extracteurs disponibles : SE16 → IXTRCTNENBLDVW sur SFDCLNT223.

Flux S/4 :

SFD [CMMPURORDAADEX] —ODP_CDS / SFDCLNT223—→ BFD [HA_CMMPURORDAADEX] → Transfo → DTP → WMMPU002
SFD [CMMPOITMDEX] —ODP_CDS / SFDCLNT223—→ BFD [HA_CMMPOITMDEX] → Transfo → DTP → WMMPU001

4.2 Architecture des ADSOs

ADSO A750PURC1 – Acquisition historique BW 7.5 (couche A)

Cet ADSO reprend la structure complète du cube source 0PUR_C01 avec toutes ses dimensions et tous ses indicateurs. Il sert de zone de staging fidèle à la source, sans transformation ni filtrage.

Type : Standard DataStore Object, Write Change Log activé, Unique Data Records désactivé (0REQTSN comme clé technique).

ADSO WMMPU001 – Postes commande d'achat S/4 (couche W) — TABLE PILOTE

ADSO alimenté par la CDS CMMPOITMDEX. C'est la source principale pour le flux S/4 : elle contient les données poste (SUPPLIER, MATERIALGROUP, PURCH_ORG) ainsi que les montants (NETAMOUNT) et quantités (ORDERQUANTITY) de référence au niveau poste. Les KPIs doivent être pris prioritairement depuis cet ADSO.

Source : SFDCLNT223 via ODP_CDS • Delta : CDC automatique.

ADSO WMMPU002 – Imputations commande d'achat S/4 (couche W) — ENRICHISSEMENT

ADSO alimenté par la CDS CMMPURORDAADEX. Apporte en complément les dimensions d'imputation comptable (GL_ACCOUNT, WBS_ELEMT, FUND, FM_AREA) qui n'existent pas au niveau poste. Joint à WMMPU001 via un LEFT JOIN sur EBELN + EBELP.

Source : SFDCLNT223 via ODP_CDS • Delta : CDC automatique.

Attention : ne pas utiliser les montants/quantités de WMMPU002 car ils sont ventilés par ligne d'imputation (split accounting).

Vue unifiée – CV_ACHAT_UNIFIED (couche R)

Calculation View ou CompositeProvider qui unifie les données historiques (A750PURC1) et courantes (WMMPU002 + WMMPU001) sur les 7 dimensions + 2 KPIs du périmètre POC.

Architecture de la vue :

NœudTypeDescription
1. LEFT JOINJoinWMMPU001 (postes, base) + WMMPU002 (imputations, enrichissement) sur EBELN + EBELP → récupérer GL_ACCOUNT, WBS_ELEMT, FUND
2. UNIONUnionA750PURC1 (historique 7.5) + résultat du JOIN (flux S/4) + champ calculé SOURCE_SYSTEM
3. ProjectionProjection7 dimensions + 2 KPIs + SOURCE_SYSTEM

Point d'attention – Imputations multiples : Une commande d'achat peut avoir plusieurs lignes d'imputation (split accounting). Le champ MULTIPLEACCTASSGMTDISTRPERCENT dans WMMPU002 indique le pourcentage de répartition. Les KPIs sont déjà ventilés au niveau imputation.
